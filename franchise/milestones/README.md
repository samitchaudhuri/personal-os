# Milestone generator

Computes a site's milestone dates from one set of durations in `durations.yaml`, so the Junction milestones table in `vault/Notes/ULC Franchise Project.md` stops drifting from the plan when the lease or opening date moves. The method and the reason for a single durations file are in the vault note under "Plan for generating the milestone tables". Task: `ulc-milestone-generator`.

## Terms

A milestone is a dated event, such as lease signed. An input is a milestone whose date the site gives, and every input has a status. Committed means somebody fixed the date, estimated means a forecast, and assumed means a date we plan around until someone commits. An estimate is a duration someone forecasts, such as Fibr's 45 days from sourcing to an accepted offer. A requirement is a duration someone needs to hold, such as the Counter LOI's 60 days to submit permits. A preference is a duration someone wants and would give up, such as Michelle Tomko's three weeks between the GM and launch, which she wants but does not require. A not-before rule is an estimate or requirement with a start and no end, such as at least 10 days after permits. A collision is a set of rules that cannot all hold, so some milestone has no possible date.

## Purposes

The opening timeline CSV is the ULC Los Gatos opening schedule as a task list, for reviewing the schedule and importing it into a Gantt tool. It has every task in order, with the dates the generator gives, the rule and preference that place each one, why, and the department. Nothing reads it.

The ramp workbook's Milestones sheet is the generator's earliest and latest date for each Site 1 milestone, keyed by name. The ramp's Draws and Sites formulas look up a key there to place each draw. The workbook's Inputs, Phases and Rules set aside sheets are the rest of the same generator run, and nothing looks them up.

## Files

`durations.yaml` holds one row per milestone, the list of rules between milestones, and four phases. Each rule says the second milestone falls within a duration range, in days, of the first, and the range can be negative, such as the GM 21 days before presale launch. A milestone reached by several rules gets the intersection of all of them, and each rule narrows both ends, so the GM preference narrows launch given the GM and the GM given launch. Keys are stable names that vault goals and targets link to.

A not-before rule is written with `null` as the upper limit, such as `[10, null]`. `construction-start` has two, delivery and permits plus 10 days. It starts as soon as the later one allows, so its latest date is the later of their latest dates. Rent commences works the same way, 150 days after the later of delivery and permits. A not-before rule marked `check: true` only checks the earliest date and does not start its milestone, such as the presale kit ordered at least 14 days before the GM is in seat.

A site must give every milestone marked `input: true`, such as the kickoff call, the lease range, the GM sourcing date and landlord delivery, and must record a status for each in the site's `status` block. The generator computes every other milestone. A milestone marked `site_can_fix: true`, such as `permits-submitted`, `permits-received`, `vip-start`, `presale-launch` and the three presale prerequisites, takes a date from the site when the site gives one. That date replaces the estimates that compute the milestone, and requirements on it still apply. Junction assumes `landlord-delivery` is 2/8, the latest date permits can be approved, so that delivery never delays construction. A date the landlord commits to replaces it with a committed status. An earlier date changes nothing, and a later one moves the earliest build dates at once and the latest ones once it passes 2/18.

Equipment, A/V and millwork have separate dates. `equipment-ordered` falls 45 to 60 days before soft open, which is Don Michael's timing from 10/14 for the $478K invoice. Samit's position is that the invoice is paid before the order is placed, so one date stands for both and the funding ramp draws from it. `av-ordered` sits 84 days before `equipment-installed`, the franchisor template's 12-week A/V lead time, and it stays an estimate until MMP confirms it. The FDD prices the millwork and lighting system at $65,000 to $100,000 as a separate franchisor purchase that the equipment invoice does not include, so `millwork-lighting-ordered` is its own milestone. Jason Park said on 10/14 that millwork, flooring, lights and A/V are paid around construction start, so it sits at construction start until its lead time is confirmed. Flooring is part of the GC's net leasehold improvements and has no order of its own. The equipment, A/V and millwork chains do not meet, so the model leaves open whether the equipment invoice includes A/V. Adding a rule that A/V is ordered after the equipment order would collide by 45 days, because an A/V order 60 days before soft open arrives 24 days after it.

A phase is a rule that also has a table row: `permit-review`, `presale-setup`, `presale-vip-booking` and `presale-membership-sales`. The last one bounds `soft-open` from launch, so the build and the sales window must agree. The generator still flags any phase whose actual span falls outside its range, which today happens when a date from the site replaces the estimate.

When the rules cannot all hold, the generator flags the collision. It names the requirement and the estimates in the loop, walks the dates around the loop, and says how many days the estimates must improve in total for the requirement to be met. It sets one rule aside to draw the dates, a preference if the collision has one, else a requirement, else the estimate listed last, so list the checks last. A preference computes dates exactly as a requirement does, but when it is the rule set aside the generator prints a softer `warning:` line, "ideal missed by N days", and not a `flag:` collision. A not-before rule is never set aside. The Flags list under the milestone table names each rule set aside, its kind, the days short and the rules it collides with. Today the warning says the GM-in-seat preference misses its ideal by 4 days, because a 12/21 launch needs the GM in seat by 11/30 and the offer accepted by 11/16, and 45 days from sourcing gives 11/20.

`sites.yaml` holds each site's inputs, such as the lease signing target and the soft-open date, plus the contract limits the generator flags against. The contract dates are copied from the vault's Contract dates table and are not computed.

`milestones.py` solves the rules as a network of date ranges, finds collisions as negative cycles, and prints a milestone table. The table has a Status column: committed, estimated or assumed for an input, and computed for a date the rules derive. A lease range that other rules narrowed shows the narrower range with the range the site gave in its status. Under the table, a Flags list names each rule set aside and each phase outside its planned length, and it is left out when nothing is off. With `--write NOTE` it rewrites the block between `<!-- milestones:SITE:start -->` and `<!-- milestones:SITE:end -->` in that note and fails if the markers are missing.

`timeline_csv.py` exports the opening timeline workbook to a CSV for a Gantt tool, one row per task, numbered 1 to N in the order shown and no longer the workbook's row numbers. The columns run from the most to the least read: `id`, `milestone`, `key`, `start`, `end`, `duration`, `rule`, `preference`, `why`, `department`, `phase`, then the cross-reference block `sample_row`, `sample_start`, `sample_end` and `sample_duration`. `milestone` is the workbook task name, without side notes in parentheses on a row that has a key, and `key` is the stable milestone name from `durations.yaml`, blank for a row the generator does not date. `sample_row` is the row in the workbook, blank for a row added from `durations.yaml`. Each rule reads like `45 days after 32`, `at least 10 days after 17`, `on or after 18`, `45-60 days before 35` or `after 7` and comes from the `durations.yaml` estimates and requirements that date that row's milestone, on the later milestone only, except that a rule written with a negative duration, such as an order 45 to 60 days before soft open, reads `before` on the earlier milestone, with a milestone that has no row named by its key, and any proposed predecessor from `timeline-dependencies.yaml` that no rule covers reads `after 7`. Rules with the same duration merge and sort, so the bare predecessors come first as `after 15, 16`, then each duration with its predecessors in order, rows before milestone keys. The `preference` column holds the ideals, such as `21 days after 27`, so a blank cell means the row has none and the rule column holds only what must hold. The `duration` column is the days from `start` to `end`. With `--site` it fills the milestone key and the generator's dates in the `start` and `end` columns for each row that `durations.yaml` maps and leaves them blank for the rest, and when several milestones share a row the first one listed wins. Row 25 stays on `equipment-ordered`, which now stands for both the order and the invoice payment. A milestone the template has no bar for takes a row of its own right after the row it shares, set by its `gantt_row` in `durations.yaml`, so `permits-received` and `landlord-delivery` follow row 26 and `av-ordered` follows row 25, and the rows after them move down one each. A rule on one of those rows also covers the row it follows, so `construction-start` no longer lists `after 26` as well. The template's bars are the sample timeline shifted to the workbook's anchor date in B2, and they sit at the right as `sample_start`, `sample_end` and `sample_duration`. The export leaves out the workbook rows in `SKIP_ROWS`, which are not milestones: 13 Register DBA, 21 Lease negotiation, 33 Naming Convention, 35 CRM Set Up, 36 Payroll Provider Selection, 40 Weekly presale 1:1 calls, 42 Grassroots Marketing, 44 Longevity Advisor Recruiting, 47 Soft opening and VIP party planning and 48 Final membership closeout. `--skip 13,33` replaces that list, an empty `--skip ""` keeps every row, and a skipped row's predecessors pass to its successors. The script stops if the list names a row the generator dates. Rows run grouped by phase and in increasing start order within each phase, by the generator's start where there is one and else the sample start, so a milestone added from `durations.yaml` takes its place by date and not right after the row it shares. Rows that tie keep their predecessors first.

`ramp.py` keeps the funding ramp workbook, `ULC Funding Ramp.xlsx`, on the generator's dates, so a draw cannot sit on a date the schedule has moved. The path is `outputs.ramp` in `sites.yaml`. The workbook's Draws tab names a milestone key as each Site 1 draw's anchor, such as `construction-start`, and gives start and end durations in days from that milestone's earliest and latest dates. The Sites tab's lease, delivery and open dates for Site 1 look up `lease-signed`, `landlord-delivery` and `soft-open`, and Sites 2 and 3 chain from Site 1's open date. Four tabs come from a fresh generator run and are the only generated schedule output in the workbook: Inputs, Milestones, Phases and Rules set aside. Inputs and Milestones keep Key in column B with the start in D and the end in E, and the Draws and Sites lookups read Milestones. `ramp.py sync` rewrites the four tabs, deletes the old Timeline tab, points any lookup that still names it at Milestones, and restores the workbook's charts. `timeline_csv.py` runs the sync whenever it rewrites the published CSV for a workbook that has a Milestones or Timeline tab, so regenerating the timeline updates the ramp. `ramp.py check` fails when a generated tab differs from a fresh generator run, when a draw names a key the generator does not date, when a keyed draw or a Site 1 date has a typed date, or when the workbook's saved dates disagree with the generator, and the pre-commit hook runs it for any commit that touches this folder. It lists the Site 1 draws still on typed dates, which no milestone moves. The sync stops while Excel has the workbook open, and the workbook recalculates when Excel opens it, or at once with `--recalc`, which has Excel save it.

`tasks.py` keeps vault task due dates on the generator's dates. A task that delivers a milestone carries `[milestone:: key]` after its description, or `[milestone:: key, earliest]` to take the earliest end of the key's range, and the default is the latest end, the date by which the work must be done. `check` lists every open tagged task whose due date differs and exits 1 when one does, and `sync` rewrites those due dates or adds one when a task has none. An unknown key stops it. A task with no tag keeps its hand-set date, which is the right result for work no milestone covers. The note path is `outputs.tasks` in `sites.yaml`, and `--note` replaces it. `milestones.py --write` runs the same sync after it rewrites the table, so the tagged dates follow without a separate step. The vault is not under this repo's pre-commit hook, so run `check` by hand after editing a tagged task's date. `actuals` is the one flow from task to milestone. A checked tagged task has a `✅` date, and when its milestone is an input or marked `site_can_fix`, that date is written into the site's inputs in `sites.yaml` as committed, with the task id in the comment, and `--write` does this first. A computed milestone is never set from a task. The runbook in the vault explains how milestones and tasks relate.

## Run

```bash
cd franchise/milestones && ./.venv/bin/python milestones.py junction
```

```bash
cd franchise/milestones && ./.venv/bin/python timeline_csv.py --site junction --out "$HOME/Library/CloudStorage/GoogleDrive-samit.chaudhuri@gmail.com/My Drive/Work/Franchise/ULC-Personal/Development/Opening Timeline/ULC Los Gatos Opening Timeline.csv"
```

Run `ramp.py check` any time to see whether the ramp follows the generator, and `ramp.py sync` to refresh it by hand.

```bash
cd franchise/milestones && ./.venv/bin/python ramp.py check
```

For TeamGantt, add `--teamgantt` to write its work-breakdown layout, with WBS numbers as predecessors. It uses the same skip list, which leaves 30 of the workbook's 41 tasks, under the free plan's 40; the script warns when the count exceeds 40.

Flags and warnings go to stderr: a collision between rules, an ideal that a preference misses, a phase whose actual span is outside its planned range, a lease date after the Site Acquisition Deadline, a soft open past the Opening Deadline with the extension fee, a GM date after the hard stop before the owner's absence, and any milestone wholly inside that absence.
